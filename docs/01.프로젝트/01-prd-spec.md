## 📌 1. 서비스 정체성 & 핵심 가치

모아보고(MoaBogo)는 **"1인 다중 가계부"**, **"비로그인 게스트를 포용하는 독립 모임 정산/게임"**, **"생활 밀착형 모아 3대 확장 서비스(당번/용돈/빌림)"**를 결합하여 개인과 공동체의 자산 흐름을 투명하고 유연하게 연결하는 스마트 라이프 플랫폼입니다.

### 3대 핵심 설계 철학
1. **Zero-Onboarding (가입 즉시 완성)**: 회원가입 완료 즉시 기본 개인 가계부가 자동 생성되며, 복잡한 설정 없이 바로 지출을 기록할 수 있습니다.
2. **거래 원자성 및 단일 귀속성 (Single Ledger Ownership)**: 하나의 거래는 오직 하나의 가계부에만 귀속되며, 가계부 간의 복제나 비대한 양방향 분개 없이 오직 명시적 이체(`TRANSFER`)로만 경계를 넘나듭니다.
3. **게스트 소멸성 인스턴스(Ephemeral Instance)**: 모임 정산 및 집안일 당번은 회원 가입 없이도 참여할 수 있으며, 게스트 내역은 복잡한 사후 소급 없이 해당 모임 인스턴스 이력으로 안전하게 완결됩니다.

## ⚙️ 3. 핵심 유스케이스 (Use Cases) 상세 명세

### UC-01: 1인 다중 가계부 스위칭 및 독립 장부 운영
- **주요 액터**: 회원 (Owner, Member, Viewer)
- **기본 흐름**:
  1. 시스템은 사용자가 소유하거나 참여 중인 가계부 목록을 조회합니다 (`PERSONAL`, `GROUP`).
  2. 사용자는 상단 칩을 클릭하여 가계부 컨텍스트를 즉시 전환합니다.
  3. 모든 지출/수입 등록은 현재 선택된 단 하나의 가계부에만 100% 원자적으로 저장되며, 타 가계부로 자동 복제되지 않습니다.

### UC-02: 2단계 OCR 비동기 파싱 및 0원 Fallback 파이프라인
- **주요 액터**: 가계부 구성원
- **기본 흐름**:
  1. 사용자가 영수증 이미지를 캡처/업로드합니다.
  2. 시스템은 이미지 SHA-256 해시를 생성하여 중복 업로드 여부를 검증하고, 백엔드 세마포어 큐에 접수 후 즉시 `task_id`를 반환합니다.
  3. **1차 로컬 처리**: 우분투 Docker EasyOCR이 백그라운드에서 가맹점, 금액, 일자, 품목을 추출합니다.
  4. **2차 Fallback 가드레일**:
     - 가맹점 인식 실패, 금액 0원 등 유효성 검증 실패 시 `flagged_fields`를 지정하고 수동 보정 모달을 호출합니다.
     - 사용자가 자신의 개인 Vision API Key(Google/OpenAI)를 등록한 경우, 개인 키로 2차 정밀 분석을 수행하여 서버 운영비 0원을 유지합니다.
  5. 검증 완료 후 지정 가계부의 `transactions` 테이블로 즉시 기장됩니다.

### UC-03: 독립 모임 정산 (1/N, 게임) 및 딥링크 간편 송금
- **주요 액터**: 모임 주최자 및 참가자 (회원/게스트)
- **기본 흐름**:
  1. 주최자는 가계부 종속 없이 1/N 정산, 사다리타기, 술래잡기를 즉시 실행합니다.
  2. 참석자 목록에서 회원을 선택하거나 미가입 게스트(예: '친구A')를 추가합니다.
  3. 총 정산 금액 입력 시 시스템이 인원수대로 절사 분할 계산합니다.
  4. 결과 화면에서 토스/카카오페이/네이버페이 딥링크 버튼을 제공하여 3초 만에 송금을 완료합니다.
  5. 정산 데이터는 해당 모임 인스턴스 내에서 소멸성으로 보존되며, 타인의 가계부에 강제로 채무를 생성하지 않습니다.

### UC-04: 적응형 벤토 대시보드(SCR-DSH-01) 및 가계부 책꽂이·활동이력·게스트홈 UX 고도화
- **주요 액터**: 회원 (가구주, 가족 구성원, 개인 사용자)
- **핵심 흐름**:
  1. **가계부 책꽂이 (Bookshelf & Deck)**: 관리 중인 가계부 열거 및 그리드(카드)/리스트 뷰어 아이콘 전환 지원. 가계부 추가 카드는 홀수로 여백이 남을 때만 조건부 노출.
  2. **요청된 머니 (Inbound Money)**: 따뜻하고 세련된 웜 앰버 골드 톤으로 전환, '수신청구/유일한' 불필요 문구 제거. 사용자 직접 정산/머니 요청 등록 모달 지원, 승인 후 송금 딥링크(토스/카카오페이/계좌 복사) 안내 마감.
  3. **순수 생활비 자산이동 분리집계**: TRANSFER 자산이동(분리됨)의 개념 안내 및 금액과 줄바꿈 분리 가독성 확보.
  4. **모바일 최적화 및 명칭 단일화**: '머니등록', '수행등록'으로 명칭 정제. 모바일 상단 툴바(검색/설정) 및 1:1 균등 액션 그리드 배치.
  5. **활동이력 (Activity Feed) 고도화**:
     - 타이틀 '활동이력' 단일화.
     - 목록(List) 및 카드(Card) 뷰어 모드 아이콘 토글 제공.
     - 최근 건수 설정: 5건, 10건, 20건 선택 세그먼트 컨트롤.
     - 페이징 처리 및 5줄 초과 시 세로 스크롤(`max-h-[380px] overflow-y-auto`) 지원.
  6. **로그인 전용 게임 프리셋 관리**: 로그인 사용자의 자주 쓰는 모임 멤버 매핑 및 맞춤 프리셋 저장/원클릭 플레이.
  7. **장부관리 화면 복구 (< 아이콘)**: 장부관리 이동 후 원클릭 대시보드 복귀 내비게이션.
  8. **비로그인 게스트홈 5대 정제**:
     - 정산 프리셋(1만, 3만, 5만, 8만, 10만) 영역의 불필요한 가로 스크롤 완전 삭제 및 유연한 flex-wrap 칩 배치.
     - 버튼명 직관화: '목표 셔플' ➔ '목표 재배치', '주사위 셔플' ➔ '사다리 재배치'.
     - 정산 인디케이터: 좌측 고정 증감([+만원-], [+천원-]), 중앙 프리셋 칩, 우측 고정 초기화.
     - 사다리 중복 가로줄 분포 안내 문구 삭제 및 결과 닫기 버튼 후방 재배치.

## 🔄 4. 모아당번 (MoaDuty) 직교 3축 상태머신 전이 매트릭스

당번 과업의 진행 상태와 승인 여부를 억지로 하나의 컬럼에 합치지 않고, **1) 수행자의 진행상태(Progress)**, **2) 가계부 정책에 따른 완료인정(Fulfillment)**, **3) 호스트 사후 평가(Evaluation)**의 3대 직교(Orthogonal) 축으로 분리하여 설계합니다.

```mermaid
graph LR
    subgraph Axis1["축 1. 진행 상태 (progress_status)"]
        S1["ASSIGNED<br/>(할당/진행중)"] -->|수행자 사진/증빙 제출| S2["ENDED<br/>(수행 종료 - 팩트 존중)"]
    end

    subgraph Axis2["축 2. 완료 인정 여부 (is_fulfilled)"]
        F1["is_fulfilled = TRUE<br/>(자율승인 모드: ENDED 즉시 인정)"]
        F2["is_fulfilled = TRUE<br/>(승인필수 모드: 호스트 확인 후 인정)"]
    end

    subgraph Axis3["축 3. 호스트 평가 & 대신수행 (Review & Audit)"]
        R1["평가/피드백:<br/>evaluation_status (EXCELLENT/NORMAL/NEEDS_CARE)<br/>rating (별점), review_memo"]
        R2["대신수행 추적:<br/>substituted_by_id, substitute_reason"]
    end

    S2 -.->|자율승인 정책| F1
    S2 -.->|호스트 확인| F2
    S2 -.->|사후 피드백| R1
```
*다이어그램 설명: 수행자가 과업을 마치고 증빙을 제출한 사실(`ENDED`)은 불변으로 존중됩니다. 가계부 설정(자율승인 vs 승인필수)에 따라 `is_fulfilled` 완료 플래그가 매핑되며, 호스트는 수행 상태를 되돌리지 않고 독립된 평가 축(`evaluation`)을 통해 칭찬과 피드백을 기록합니다.*

### 상태머신 전이 매트릭스 (Transition Matrix)

| 구분 | 컬럼 / 속성 | 상태 값 | 액터 | 전이 조건 및 비즈니스 룰 |
| :--- | :--- | :--- | :---: | :--- |
| **진행 상태** | `progress_status` | `ASSIGNED` ➔ `ENDED` | 수행자 | • 사진 URL 또는 수행 메모 제출 필수.<br>• 수행자가 완료 선언한 팩트(Fact)는 호스트가 임의 취소 불가. |
| **완료 인정** | `is_fulfilled` | `FALSE` ➔ `TRUE` | 시스템 또는 호스트 | • **자율승인 모드**: `progress_status == ENDED` 도달 시 시스템이 즉시 `TRUE` 확정.<br>• **승인필수 모드**: 호스트 확인 클릭 시 `TRUE` 확정.<br>• **영구 보존 원칙**: 추후 가계부 정책이 바뀌어도 이미 `TRUE`가 된 과거 완료 내역은 절대 소급 취소되지 않음. |
| **호스트 평가** | `evaluation_status` | `PENDING` ➔ `EXCELLENT` / `NORMAL` / `NEEDS_CARE` | 호스트 | • 과업 종료 후 호스트가 별점(`rating: 1~5`) 및 피드백 메모 등록.<br>• 수행자 포인트 기여도에 반영. |
| **대신수행** | `substituted_by_id` | 회원 UUID | 대신 수행자 | • 원래 배정자(`assigned_user_id`)와 대신 수행자(`substituted_by_id`)를 분리 기록하여 투명성 보장. |

## 🔗 5. 게스트(Guest) 소멸성 인스턴스(Ephemeral Instance) 격리 원칙

게스트 활동을 나중에 회원가입할 때 억지로 찾아내어 DB를 대규모 UPDATE하는 복잡한 소급 매핑(Retrospective Mapping)을 완전히 배제하고, **소멸성 인스턴스 격리** 원칙을 확립합니다.

```mermaid
sequenceDiagram
    autonumber
    actor Guest as 미가입 게스트 (친구A)
    actor Host as 모임 호스트 (구본영)
    participant Event as 독립 이벤트 인스턴스
    participant Ledger as 가계부 (Ledger)

    Host->>Event: 1/N 정산 생성 (참가자: 게스트 '친구A' 39,000원)
    Note over Event: 게스트 고유 participant_id 부여 (타 모임과 완전 격리)
    Guest->>Event: 링크 접속 후 39,000원 확인 및 토스 딥링크 송금
    Event->>Event: is_settled = TRUE (해당 인스턴스 내에서 종결)
    
    Note over Guest,Ledger: [소멸성 원칙] 추후 게스트가 회원가입을 하더라도 과거 내역을 소급하지 않음!<br/>과거 내역은 해당 모임 영수증의 박제된 이력으로만 안전하게 보존됨.
    
    Host->>Ledger: [비용이동 제안] 가계부로 정산 지출 기장 제안
    Ledger-->>Host: 당사자 승인(Opt-in) 후 가계부 최종 반영
```
*다이어그램 설명: 게스트 '친구A'의 활동은 해당 모임 인스턴스 안에서만 고유한 `participant_id`로 식별되며, 모임 종료 시 인스턴스 이력으로 완결됩니다. 사후 회원가입 시 복잡한 소급 매핑을 수행하지 않으며, 비용 이동은 당사자의 승인 절차를 통해서만 이루어집니다.*

### 게스트 관리 3대 단순화 규칙
1. **모임 한정 식별자(Participant ID)**: 게스트의 닉네임은 단순 표시용이며, 모임 인스턴스별 고유 ID(`participant_id`)로 독립 식별되어 타 모임과 절대 섞이지 않습니다.
2. **사후 소급 배제(No Retrospective Mapping)**: 게스트가 나중에 모아보고에 회원가입을 하더라도, 과거 게스트 내역을 억지로 찾아 계정에 붙이지 않습니다. 시스템 프로세스 비대화를 원천 차단합니다.
3. **비용 이동 당사자 승인(Opt-in) 필수**: 타인의 가계부에 채무나 비용을 일방적으로 밀어 넣을 수 없으며, 제안 ➔ 수락의 상호 확인 절차가 선행되어야 합니다.

## 💰 6. 가계부 활동의 원자성과 금전관리 3대 정책 (Money Management Axioms)

급여, 로또, 비자금, 용돈, 가족 생활비가 뒤엉켜 계산이 폭주하는 현상을 막기 위한 **단순하고 일관된 3대 금전관리 공리(Axioms)**를 규정합니다.

```mermaid
graph TD
    subgraph Personal["[개인 가계부] - 100% 독립된 사적 영역"]
        P_INC["수입: 급여 500만, 로또 10만"]
        P_EXP["지출: 개인 커피 5천, 비자금 취미 10만"]
        P_TRF["이체(유출): 가족 생활비로 200만 이체"]
    end

    subgraph Group["[우리집 가계부] - 100% 독립된 공동체 영역"]
        G_TRF_IN["이체(유입): 개인 가계부로부터 200만 유입"]
        G_EXP["순수 생활비 지출: 마트 12만, 관리비 25만"]
        G_ALLOW["가족 내부 이동: 자녀에게 용돈 5만 건넴 (TRANSFER)"]
    end

    subgraph Child["[자녀 가계부] - 독립 사적 영역"]
        C_INC["수입: 부모에게 받은 용돈 5만 (INCOME)"]
        C_EXP["지출: 편의점 삼각김밥 1,500원 (EXPENSE)"]
    end

    P_TRF ==>|오직 TRANSFER로만 연결| G_TRF_IN
    G_ALLOW ==>|오직 TRANSFER로만 연결| C_INC
```
*다이어그램 설명: 개인과 그룹 가계부는 완전히 독립된 원자적 장부이며, 서로의 장부를 침범하지 않습니다. 가계부 간의 연결은 오직 '이체(TRANSFER)'라는 명시적 자금 이동 통로로만 이루어지며, 복잡한 자동 분개나 양방향 복제는 발생하지 않습니다.*

### UC-05: 가계부 vs 용돈기입장 및 단기(정산형) vs 장기(연속형) 회계 관리 프로세스
- **주요 액터**: 회원 (가구주, 가족 구성원, 개인 사용자, 자녀, 모임 총무)
- **핵심 흐름**:
  1. **가계부(Household) vs 용돈기입장(Pocket Money) 도메인 분리**:
     - **가계부 (`sub_type = 'STANDARD'`)**: 다중 자산(은행/카드/현금) 수지 및 총 순자산 변동 결산 중심의 포괄적 회계 장부.
     - **용돈기입장 (`sub_type = 'POCKET_MONEY'`)**: 독립 장부 유형으로 분리되며, 지정된 한도(예산 `budget_cap`) 내에서 실시간 지출 소진율(Spent Ratio)과 잔여 용돈(Remaining Cap)을 통제하는 직관적 단일 수지 체계.
  2. **단기 장부(정산형) vs 장기 장부(연속형) 생명주기 및 마감(Closing)**:
     - **단기 장부 (`period_type = 'SHORT_TERM'`)**: 여행, 워크숍, 일회성 이벤트 등 정산 중심. '진행(`OPEN`) ➔ 지출 누적 ➔ N빵/차액 정산 ➔ 마감(`CLOSED`/`SETTLED`)' 흐름을 따르며, 마감 시 읽기 전용(Read-Only) 보관으로 전환되고 최종 결산 영수증(Closing Statement)을 제공. 장부 생성 시 설정(`allow_reopen`)에 따라 방장의 마감 취소/재오픈 지원.
     - **장기 장부 (`period_type = 'LONG_TERM'`)**: 일상 가계부, 부부 공동 가계부 등. 기간 제한 없이 영속 운영되며 월별 결산 마감 후 잔액이 다음 달로 차기 이월(Carried-Over)되는 시계열 누적 관리.
  3. **장부책장(SCR-LED-01) 시각적 분류 및 상태 표시**:
     - 상단 탭 필터: `전체` | `모임 가계부` | `개인 가계부` | `용돈기입장` | `단기 프로젝트`.
     - 책등(Spine) 인장: 단기/장기 리본 뱃지, 용돈기입장 식별자, 정산 완료 시 금박 마감 인장(Seal) 표기.

### 원칙 1. 단일 거래의 단일 가계부 귀속성 (Single Ledger Ownership)
- 모든 거래는 **오직 하나의 가계부(Primary Ledger)**에만 기록됩니다.
- 한 가계부에서 지출이나 수입을 등록했다고 해서 다른 가계부로 데이터가 복제되거나 미러링되지 않습니다 (원자성 100% 유지).
- **급여, 로또, 비자금**: 오직 `[개인 가계부]`에서만 발생하며, 그룹 가계부는 이 내역의 존재 자체를 알 필요가 없습니다 (완벽한 사생활 보장).
- **가족 공금 마트 장보기**: 오직 `[그룹 가계부]`에만 1건 기록됩니다.

### 원칙 2. 가계부 간의 경계는 오직 '이체(TRANSFER)'로만 연결 (1:1 자기참조 페어링)
- **개념**: 통장 간 이체, 부모-자녀 간 용돈 지급, 모임 회비 송금 등은 자산의 보관 장소(장부/계좌)만 이동하는 것이므로 가계 전체 관점에서 **수입도 지출도 아닌 자산 재배치**입니다.
- **이중계상(Double Counting) 원천 방지 (`is_asset_transfer = true`)**:
  - 자금 이동 시 순수 생활비/소비 통계 집계에서 자동 제외하여 가계 지출이 2배로 뻥튀기되는 왜곡을 차단합니다.
- **1:1 자기참조 페어링 (`related_transfer_id`)**:
  - 출금 레코드(Tx-Out)와 입금 레코드(Tx-In)가 서로의 `transaction_id`를 `related_transfer_id`로 맞물려 참조합니다.
  - 한쪽의 금액/일자 수정 시 반대편도 자동 동기화되며, 삭제 시 반대편도 연쇄 취소되어 장부 간 잔액 오차를 원천 방지합니다.
- **실생활 적용 사례**:
  1. **부모 $\rightarrow$ 자녀 용돈 지급 10만 원**:
     - 부모 가계부: `[출금] 100,000원 | TRANSFER | 상대: 자녀 용돈기입장 | is_asset_transfer: true | related_transfer_id: Tx-2`
     - 자녀 용돈기입장: `[입금] 100,000원 | TRANSFER | 상대: 부모 가계부 | is_asset_transfer: true | related_transfer_id: Tx-1`
     - 👉 **결과**: 가구 총 순자산 변동 0원, 생활비 지출 0원. 이후 자녀가 용돈기입장에서 **"편의점 간식 5,000원(EXPENSE)"**을 썼을 때 비로소 가구 소비 지출 5,000원으로 정확히 집계됩니다.
  2. **개인 가계부 $\rightarrow$ 제주도 여행(단기 모임) 회비 20만 원 납부**:
     - 개인 가계부는 20만 원 유출(`TRANSFER`), 여행 장부는 20만 원 유입(`TRANSFER`). 여행 현지에서 식비/숙박비 결제 시 비로소 모임 지출(`EXPENSE`) 집계.

### 원칙 3. '결제자(Payer)'와 '대상자(Beneficiary)'의 단순 태깅 분리
- 가족 가계부에서 10만 원 마트 장을 아빠 카드로 긁었을 때:
  - 가족 가계부에 지출 10만 원 1건 기록 (`EXPENSE`, 100,000원).
  - 속성 태그만 기록: 결제자(`payer: 아빠`), 사용처(`beneficiary: 가족전체`).
  - 이것을 아빠 개인 가계부로 복제하지 않습니다. 아빠는 가족 가계부에서 "내가 이번 달 가족을 위해 카드로 긁어준 금액" 필터로 확인하면 끝납니다.

### 회계 집계 공식
$$\text{순수 생활비 지출} = \sum \text{amount} \quad (\text{WHERE } \text{transaction\_type} = \text{'EXPENSE'} \land \text{is\_asset_transfer} = \text{FALSE})$$

$$\text{순수 가계 수입} = \sum \text{amount} \quad (\text{WHERE } \text{transaction\_type} = \text{'INCOME'} \land \text{is\_asset_transfer} = \text{FALSE})$$

### UC-06: 전역 원자 지출(SSOT) 기반 N개 멀티 증빙 체인 및 명세서 대사 관리
- **주요 액터**: 회원 (개인 사용자, 가족/모임 총무)
- **핵심 흐름**:
  1. **전역 원자 지출(Atomic Expense SSOT) 단일성**:
     - 시스템에서 발생한 실제 결제 사건(Financial Event)은 시스템 전역에서 오직 1건만 유일하게 생성·관리됩니다.
     - 가계부(개인, 모임, 용돈기입 등)는 이 원자 지출을 직접 소유하는 것이 아니라 **참조 및 귀속(Ledger Allocation)**하는 뷰(Projection)입니다.
     - 장부에서 특정 지출을 제외하거나 장부가 삭제되어도, 원자 데이터 자체는 즉시 파기되지 않고 `UNALLOCATED` 상태로 보존됩니다.
  2. **미아 데이터(Orphan/Unallocated) 수명주기(TTL) 정책**:
     - 어떤 장부에도 할당되지 않고 증빙 대사도 없는 미아 데이터는 무한 누적되지 않고, 사용자 설정 기간(기본값: 90일, 30~365일 설정 가능) 동안 유예 후 백그라운드 가비지 컬렉션(GC)을 통해 안전하게 정리됩니다.
  3. **N개 무제한 멀티 증빙 체인 (Multi-Proof Chain)**:
     - 단일 원자 지출에 대해 수기 등록, 영수증 OCR 촬영, 결제 화면 캡처, 카드 승인 SMS, 월말 카드 이용대금명세서 라인 등 **발생한 모든 증빙을 N개 연결(Chaining)**하여 관리합니다.
     - 증빙이 추가될 때마다 대사 엔진이 시간/금액/가맹점을 분석하여 동일 사건으로 묶어내며, 카드명세서 접수 시 최종 청구액으로 수렴 확정(`CONFIRMED`)됩니다.
  4. **운영비 0원 온디맨드 스토리지 수명주기 (Zero-Cost Storage Tiering)**:
     - 활성기(최근 30일): WebP 압축 썸네일(15KB)과 원본 이미지를 상시 보관.
     - 보관기(30일 초과): 원본 이미지는 월별 압축 아카이브(`proofs_YYYY_MM.tar.gz`)로 패킹 보관하고, 일상 조회는 경량 썸네일만 노출.
     - 온디맨드 해제: 원본 확대 조회 시에만 임시 메모리에서 단건 압축 해제 후 팝업 종료 즉시 파기하여 홈서버 2GB RAM OOM을 원천 방어합니다.
  5. **서비스 간 변경 내성 연계 (Change-Resilient Coupling)**:
     - 가계부, 모임 정산, 당번, 미니게임은 서비스 간 시너지를 위해 유기적으로 연계되되, 도메인 이벤트(`SettlementCompletedEvent` 등) 계약을 통해 통신하여 한 기능의 변경이 다른 기능에 전파되지 않는 높은 변경 내성을 유지합니다.
