## 1. 개요 및 기술 도입 배경

모아보고(MoaBogo)는 비로그인 게스트와 가입 회원이 함께 즐기는 오프라인 모임 정산 및 게임(사다리, 룰렛)을 제공합니다.  
초기 프로토타입은 단일 브라우저 내 탭 간 동기화(`BroadcastChannel`)로 시작되었으나, **오프라인 테이블에 모인 여러 참가자가 각자의 스마트폰 카메라로 QR 코드를 스캔하거나 초대 링크를 통해 하나의 게임방에 실시간으로 입장하여 자리를 찜하고, 호스트가 사다리/룰렛을 돌릴 때 동시에 시각적으로 감상하는 크로스 디바이스(Cross-Device) 협업 경험**이 필수 요구사항으로 대두되었습니다.

본 문서는 실시간 동기화 기술 후보군을 비교 분석하고, 식별자(Room ID) 체계의 확장성, 보안 가드레일, 서버 자원 한계 극복 전략 및 운영 시 유의사항을 체계적으로 정립합니다.

## 2. 룸 식별자(Room ID) 설계 및 확장성 분석

### 2.1 기존 6자리 단일 식별자의 한계
- 기존 6자리 숫자/단순 문자 조합은 약 $36^6 \approx 21.7\text{억}$ 개이나, 사람 간 오입력 위험 및 게임 타입(`LADDER`, `ROULETTE`, `SETTLEMENT`) 구분의 모호함이 발생할 수 있습니다.
- 이후 가계부 공동 기장, 모아당번 실시간 투표, 추가 미니게임 등 다목적 확장을 고려해야 합니다.

### 2.2 모아보고 통합 룸 식별자 표준 규격 (Type-Prefixed CUID / Base32)

```
[Type Prefix (1~3)][Delimiter (-)][Nanoid/Base32 (6~8)]
예시:
• 사다리 게임: LAD-7X9K2M (또는 단순 공유용 LAD-7X9K)
• 룰렛 게임:   ROU-4M8P9Q
• 모임 정산:   SET-9W2N1K
• 통합 단축형: MOA-8F3K9L
```

1. **도메인 가독성 (Human-Readable)**: 접두사(`LAD-`, `ROU-`)만 보고도 어떤 게임방인지 즉시 식별 가능.
2. **모바일 입력 친화성 (Crockford Base32)**:
   - 혼동하기 쉬운 문자 `0`, `O`, `I`, `1`, `L` 등을 배제하여 스마트폰으로 수동 코드 입력 시 오타 발생률 0% 지향.
3. **규모 및 충돌 확률**:
   - $32^6 = 1,073,741,824$ (약 10억 개), $32^8 \approx 1조$ 개.
   - 2시간 TTL(Time-To-Live) 적용 시 동시 활성 룸 10만 개 기준 충돌 확률은 $10^{-9}$ 이하로 완벽한 유일성 보장.

## 3. 실시간 통신 기술 비교 분석 (Comparison)

| 기술 분류 | 작동 원리 및 특징 | 장점 | 단점 및 제약 | 모아보고 채택 전략 |
| :--- | :--- | :--- | :--- | :---: |
| **BroadcastChannel API** | 브라우저 탭/창 간 IPC 통신 | • 0ms 지연<br>• 서버 트래픽 0% | • 동일 오리진·동일 기기만 작동<br>• 모바일 간 통신 불가 | **[Tier 1 채택]**<br>로컬 탭 간 초저지연 연동 |
| **Server-Sent Events (SSE) + HTTP POST** | 서버 ➔ 클라이언트 단방향 스트림 (HTTP/1.1 or HTTP/2) + 경량 POST Mutation | • 표준 HTTP 기반으로 방화벽/프록시 100% 통과<br>• 자동 재연결(Built-in reconnection)<br>• 배터리 및 CPU 오버헤드 최소화 | • 클라이언트 ➔ 서버 방향은 일반 HTTP POST 사용 (Half-duplex) | **[Tier 2 주력 채택]**<br>클라우드 런 / 프록시 환경에서 가장 높은 신뢰성 |
| **WebSocket (ws/wss)** | TCP 기반 전이중(Full-Duplex) 양방향 소켓 통신 | • 양방향 초저지연<br>• 바이너리 프레임 지원 | • Cloudflare Tunnel 524 / 프록시 타임아웃 취약<br>• 연결 끊김 시 재연결 핸드셰이크 복잡 | **[선택적 하이브리드]**<br>실시간 액션 빈도가 100ms 미만인 게임으로 점진 확장 |
| **WebRTC DataChannel** | P2P 피어 간 직접 연결 | • 서버 거치지 않는 초저지연 | • STUN/TURN 서버 인프라 비용<br>• 모바일 NAT 통과 실패율 높음 | 보류 (비용 대비 효용 낮음) |

### 💡 결론 및 하이브리드(Hybrid) 통신 아키텍처
모아보고의 게임 특성상 **"호스트가 설정을 바꾸거나 돌리는 이벤트"는 초당 수천 회 발생하는 트위치형이 아니며, 초당 1~5회 수준의 상태 동기화"**입니다.  
따라서 Cloud Run, Cloudflare Tunnel, 다양한 스마트폰 LTE/5G 모바일 네트워크 환경에서 **가장 안정적이고 방화벽 차단이 없는 HTTP SSE(Server-Sent Events) + REST Mutation 파이프라인**을 코어로 두고, 동일 브라우저에서는 **BroadcastChannel**을 동시 가동하는 **하이브리드 다계층 아키텍처**가 최적의 해법입니다.

## 4. 보안, 권한 거버넌스 및 자원 방어 전략

### 4.1 참여자 권한 거버넌스 (RBAC Matrix v2.0 - 세션 0032 고도화)
- 방을 최초 생성한 기기가 `hostTabId` 및 `hostToken`을 점유.
- **방장(Host) 전용 권한**: 사다리 타기 시작(`PLAY_LADDER`), 룰렛 돌리기(`SPIN_ROULETTE`), 참가자 순서 섞기(`SHUFFLE_MEMBERS`), 방 폐기/완전 종료(`CLOSE_ROOM`).
- **게스트(Guest) 확대 권한**:
  - 사다리: 가로줄 섞기(`SHUFFLE_RUNGS`), 목표 섞기(`SHUFFLE_GOALS`).
  - 룰렛: 항목 섞기(`SHUFFLE_ROULETTE_ITEMS`), 항목 선택/체크(`SYNC_ROULETTE_ITEMS`).
  - 내 자리 점유 및 변경: 본인이 점유한 참가자(`claimedBy === tabId`)의 이름 변경, 아바타 아이콘 변경, 매장 메뉴 선택 교체(`UPDATE_MEMBER_DETAILS`).
  - 방 이탈(`LEAVE_ROOM`).
- **상태 메시지 표준화**: 자리 선택/변경 및 액션 시 피드백 알림은 3초(3,000ms) 유지 후 자동 페이드아웃 닫기.

### 4.2 Presence 정밀화 및 1.5초 연결 유예 (Grace Period)
- 클라이언트의 일시적 네트워크 재연결, 탭 새로고침 또는 리액트 언마운트/리마운트 시 SSE 연결이 순간 종료되었다가 수십 ms 내에 복구되는 현상으로 인해 동시 접속자 수가 1↔2로 펄럭거리며 깜빡이는 현상(Ping-pong)을 원천 차단.
- `req.on('close')` 감지 시 즉각적인 `connectedTabs.delete` 및 잔여 인원 브로드캐스트를 유예하고, 1,500ms 동안 `tabDisconnectTimers`를 대기.
- 동일 탭이 재연결되면 대기 타이머를 즉시 취소하고 연속 연결로 처리하며, 1.5초가 초과된 경우에만 최종 퇴장 처리 및 인원수 감소 전파.

### 4.2 DoS 방어 및 방 만료(TTL) 정책
1. **메모리 릭 방지 (Room TTL 2시간)**:
   - 마지막 활동(`lastActive`) 기준 2시간 이상 신호가 없는 방은 백그라운드 스케줄러가 메모리에서 자동 제거.
2. **접속자 상한 (Max 30명)**:
   - 모임/테이블 게임 특성을 고려하여 룸당 최대 접속자 수를 30명으로 제한하여 서버 OOM 방어.
3. **요청 쓰로틀링 (Rate Limiting)**:
   - 동일 클라이언트의 Mutation 호출은 1초당 최대 5회로 제한하여 과도한 클릭 매크로 방어.
4. **Zero-Loss 무중단 복구 (Local Storage Snapshot)**:
   - 서버 재시작 시에도 클라이언트는 로컬 스냅샷(`localStorage`)을 보유하여 재연결 시 룸 상태를 즉시 재동기화(`SYNC_REQUEST` ➔ `SYNC_STATE`).

## 5. 다중 배포 환경(샌드박스, 로컬, 개발, 검증, 운영) 호환성

- 클라이언트 코드는 정적 도메인을 하드코딩하지 않고, `window.location.origin` 및 상대 경로(`/api/v1/games/...`)를 사용하여:
  - `http://localhost:3000` (로컬)
  - `https://ais-dev-*.run.app` (샌드박스 개발)
  - `https://ais-pre-*.run.app` (샌드박스 공유)
  - `https://dev.moabogo.app` / `https://stg.moabogo.app` / `https://moabogo.app` (실서버)
  어느 환경에서 접속하든 동일한 도메인 기반의 초대 링크 및 QR 코드가 100% 무결하게 생성되도록 설계합니다.

## 6. 사다리 스마트 카메라 뷰포트 & 마일스톤 실시간 동기화 (v2.1)
- **0.5 Step(반 칸, 52px) 벽 충돌 방어 가드레일**:
  사다리 이동 중 앵커(마커)가 뷰포트 좌우 경계에 닿기 전 항상 최소 `LADDER_COL_WIDTH * 0.5` (52px)의 여유 뷰포트를 선제 확보하여 시야 차단을 원천 방어합니다.
- **순차 앵커 전환 및 스무스 패닝 (Smooth Panning)**:
  한 주자의 골인이 완료되면 다음 참가자의 최상단 시작 지점으로 뷰포트를 부드럽게 이동(Easing factor 0.25)한 후 사다리 타기를 재개합니다.
- **마일스톤 기반 동시성 제어 (`LADDER_PROCEED_NEXT`, `LADDER_COMPLETE`)**:
  매 틱의 고빈도 좌표 전송 대신 결정론적 경로 계산(동일 seed)과 마일스톤 액션 릴레이 방식을 채택하여 대역폭 소모를 최소화하면서 참가자 전원의 화면과 결과 모달 팝업 오픈을 100% 동기화합니다.
- **게스트 도착 대기 UI**:
  방장이 다음 주자를 출발시키기 전까지 게스트 화면의 도착 팝업에 안내 배지(`방장이 다음 주자를 출발시킵니다`)를 표시하여 조작 혼선을 방지합니다.
