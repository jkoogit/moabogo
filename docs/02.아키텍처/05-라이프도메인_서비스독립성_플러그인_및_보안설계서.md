## 1. 추진 배경 및 설계 목표

모아보고의 라이프 서비스 영역(모아당번, 모아목표, 모아루틴, 모아부릉 등)이 빠르게 확장됨에 따라 다음과 같은 구조적 과제가 식별되었습니다:

1. **화면 간 수평 의존성 차단**: `SCR_DUT_02`가 `SCR_DUT_01`의 내부 함수를 직접 import하는 등 도메인 간·화면 간 수평 결합은 수정 파급력을 키움.
2. **서비스 내부 차별기능의 개방-폐쇄 원칙(OCP) 확보**: 하나의 서비스 안에서도 완전히 다른 UI·로직을 가진 하위 유형(예: 모아루틴의 약복용/알뜰폰/세금계산서/급여카드, 모아목표의 저축/습관/수치)을 거대 `switch` 문으로 처리할 경우 파일이 500줄을 초과하고 유지보수성이 급감함.
3. **클라이언트 보안 및 회계 무결성 일원화**: 브라우저 로컬 저장소(`localStorage`) 민감정보 정제, 외부 송금 딥링크 안전 검증, 정산 중복 집행 방지(멱등키) 로직이 각 화면에 흩어지지 않고 단일 공통 가드레일에서 강제되어야 함.

## 2. 2-Layer 서비스 독립성 아키텍처

```text
[Shared Core Layer: src/sample/shared/] (도메인 비종속 단방향 하위 계층)
  ├─ securityGuards.ts       : PII 마스킹, localStorage 민감정보 정제, 안전 송금 URL 검증, 멱등키 생성
  └─ ledgerTransferBridge.ts : 가계부 TRANSFER(is_asset_transfer=true) 1:1 자기참조 단방향 발행 포트
          ▲                         ▲                         ▲
          │ (단방향 의존)            │ (단방향 의존)            │ (단방향 의존)
┌─────────┴──────────┐   ┌──────────┴──────────┐   ┌──────────┴──────────┐
│ 모아루틴 (routine/) │   │ 모아당번 (duty/)    │   │ 모아목표 (goal/)    │
│ · plugins/ 레지스트리│   │ · 3상태머신/상계정산 │   │ · 유형별 메트릭 플러그인│
│ · 선도 적용 완료     │   │ · BKL-ARCH-01 전환  │   │ · BKL-ARCH-01 전환  │
└────────────────────┘   └─────────────────────┘   └─────────────────────┘
```

### 2.1 절대 준수 경계 규칙 (Boundary Rules)
1. **Zero Horizontal Import**: `routine/`, `duty/`, `goal/`, `car/` 도메인 폴더 간 직접 `import`를 전면 금지합니다.
2. **단방향 포트 연동 (Port & Event Bridge)**: 루틴이나 당번이 가계부 원장에 자산이동(`TRANSFER`)이나 정산 내역을 전달할 때는 가계부 내부 컴포넌트를 참조하지 않고, 오직 `src/sample/shared/ledgerTransferBridge.ts`의 표준 계약(`publishLedgerTransfer`)을 통해서만 이벤트를 발행합니다.
3. **단일 파일 500줄 상한 (SRP Guardrail)**: 메인 화면 셸은 350줄 이내, 개별 차별기능 플러그인 파일은 250줄 이내를 유지합니다.

## 3. 서비스 내부 차별기능 관리: Strategy Plugin Registry 패턴

### 3.1 모아루틴(`routine/plugins/`) 표준 계약
각 차별기능은 `RoutinePlugin<T>` 인터페이스를 구현하고 `routine/plugins/registry.ts`에 등록합니다.

| 구성 파일 | 책임 범위 |
| :--- | :--- |
| `plugins/pluginContract.ts` | 플러그인 공통 인터페이스(`renderCard`, `getListSummary`, `renderCreateFields`, `renderDetailContent`, `evaluateUrgencyCount`, `enabled` Feature Flag) 및 공용 UI 헬퍼(`RoutineHelpTooltip`) |
| `plugins/medicinePlugin.tsx` | 💊 약복용 루틴 (처방전 OCR 요약, 아침/점심/저녁 타임라인 체크, 잔여 알약 카운트다운·보충) |
| `plugins/mvnoPlugin.tsx` | 📱 알뜰폰 환승 루틴 (5단계 D-Day FSM, 특가 vs 정상요금 절감액, 환승 체크리스트·주기 갱신) |
| `plugins/taxInvoicePlugin.tsx` | 📑 세금계산서 발급 루틴 (매월 10일 마감, 사업자번호 마스킹, 거래처별 공급가/부가세 발급 체크) |
| `plugins/cardSettlePlugin.tsx` | 💳 급여·카드 정산 루틴 (결제계좌 마스킹, 이체 체크, `ledgerTransferBridge` 연동 진입점) |
| `plugins/registry.ts` | 카테고리별 플러그인 조회(`getRoutinePlugin`), 활성화 목록 필터링(`getEnabledRoutinePlugins`) 단일 진실 공급원 |

### 3.2 확장성 및 유지보수 이점
- **신규 차별기능 추가 시 기존 코드 수정 0줄**: 예컨대 추후 '독서 루틴'이나 '구독 관리 루틴'을 추가할 때 `plugins/readingPlugin.tsx` 1개만 작성해 `registry.ts`에 등록하면 카드 뷰·리스트 뷰·등록 모달·상세 모달·KPI 집계가 자동 연결됩니다.
- **Feature Flag 제어**: 각 플러그인의 `enabled` 플래그만으로 운영/테스트 환경에서 특정 루틴을 즉시 노출·비활성화할 수 있습니다.
- **당번·목표 확장 표준**: `BKL-ARCH-01` 백로그를 통해 모아목표(`GoalMetricPlugin`)와 모아당번(`duty/` 모듈 분해)에도 동일한 경계 규칙을 일괄 적용합니다.

## 4. 공통 보안 가드레일 설계 (`src/sample/shared/securityGuards.ts`)

1. **브라우저 저장소 민감정보 정제 (`sanitizeForStorage`)**:
   - `localStorage`에 상태가 저장되기 전, 계좌번호(`accountNo`), 사업자등록번호(`bizNo`), 전화번호 등은 자동으로 마스킹 처리된 형태로 정제하여 브라우저 개발자도구·로컬 노출 위험을 최소화합니다.
   - 백엔드 PostgreSQL 연동(`BKL-DATA-01`) 시 원본 계좌·사업자번호는 서버 암호화 저장하고 클라이언트에는 식별자(`accountId`)와 마스킹 문자열만 전달합니다.
2. **외부 송금·초대 딥링크 화이트리스트 검증 (`validateSafeTransferUrl`)**:
   - 허용 스킴(`https:`, `supertoss:`, `kakaopay:`) 및 신뢰 호스트(`toss.me`, `qr.kakaopay.com`, `moabogo.app`)만 통과시키고, 그 외 비인가 링크나 스크립트 스킴(`javascript:`, `data:`)을 원천 차단합니다.
3. **멱등성 보장 키 (`buildIdempotencyKey`)**:
   - 급여·카드 정산 ➔ 가계부 `TRANSFER` 기장 시 `routineId | yearMonth | sourceAccount | totalAmount` 조합으로 결정적 멱등키를 생성하여, 더블클릭이나 오프라인 재동기화 시 중복 거래 생성을 차단합니다.
4. **안전 렌더링 원칙**:
   - 처방전 OCR 요약, 거래처명, 메모 등 모든 사용자 입력 텍스트는 React 기본 텍스트 바인딩으로만 렌더링하며 raw HTML 주입을 금지합니다.
