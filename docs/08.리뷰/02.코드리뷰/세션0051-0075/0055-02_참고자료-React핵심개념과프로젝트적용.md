## 3. 개념별 원리 및 MoaBogo 코드 연결

### 3.1 컴포넌트 조합 (Composition)

#### 핵심 원리
React는 클래스 상속이 아니라 **컴포넌트 합성(Composition)**으로 UI와 횡단 관심사(에러 격리, 테마, 레이아웃)를 조립한다.
- **`children` 포함(Containment)**: 바깥 래퍼 컴포넌트가 구체적인 자식 내용을 몰라도 `props.children`을 통해 테두리·배경·Context·ErrorBoundary를 감쌀 수 있다.
- **전문화(Specialization) 및 슬롯/전략 조합**: 공통 셸에 콜백이나 렌더 슬롯(`renderCard`, `renderDetailWidget`)을 주입해 도메인 변형을 분리한다.

#### MoaBogo 저장소 연결 예시
1. **이중 계층 횡단 조합 (`src/main.tsx:8-15`, `src/App.tsx:765-772`, `src/components/AppErrorBoundary.tsx:20-119`)**:
   - 루트 진입점 `src/main.tsx`는 `AppErrorBoundary(variant="root")` ➔ `ThemeProvider` ➔ `App` 순서로 `children` 합성을 수행한다.
   - `App.tsx:765-772`는 현재 활성 화면 `{currentScreenObj.comp}`를 다시 화면 단위 `AppErrorBoundary(variant="screen")`로 감싼다. 덕분에 한 화면에서 렌더링 예외가 발생해도 헤더/드로어 등 전체 셸이 죽지 않고 해당 화면 영역만 복구 UI(`handleRetry`, `handleResetLocalCache`)로 격리된다.
2. **전략 레지스트리 슬롯 조합 (`src/sample/screen/routine/plugins/registry.ts:19-44`, `src/sample/screen/goal/plugins/pluginContract.tsx:17-37`)**:
   - 모아루틴(`SCR_ROU_01_모아루틴.tsx:64-78`)과 모아목표는 `if/else`나 거대 `switch` 분기 대신 `RoutinePlugin`·`GoalMetricPlugin` 인터페이스를 구현한 플러그인 모듈(`medicinePlugin`, `mvnoPlugin` 등)을 `PLUGIN_LIST`로 등록하고, 렌더링 슬롯(`renderCard`, `renderDetailWidget`)을 조합해 화면을 구성한다.

#### 설계상 의미
- `children` 합성을 쓰면 상위 래퍼(`ThemeProvider`, `AppErrorBoundary`)가 하위 21개 화면을 `import`하지 않고도 모든 화면을 감쌀 수 있다. 반대로 `App.tsx:12-32`처럼 `screens` 배열이 21개 화면 컴포넌트를 직접 정적 `import`해 들고 있으면 조합의 이점(지연 로딩, 독립 번들)이 제한된다.

### 3.2 `props` / `state` 경계와 상태 소유권

#### 핵심 원리
- **`props`**: 부모가 자식에게 내려주는 읽기 전용 입력 계약이다. 자식은 `props`를 직접 변이(mutate)하지 않고, 변경이 필요할 때 부모가 내려준 콜백(`onSelect`, `onClose`)을 호출해 변경 의사를 전달한다.
- **`state`**: 컴포넌트가 시간에 따라 변하는 값을 기억하는 내부 상태다. "어느 컴포넌트가 이 상태를 소유할 것인가(Single Source of Truth)"가 설계의 핵심이다.
  - 여러 형제 화면이 공유하는 상태 ➔ 공통 조상으로 **끌어올리기(Lifting State Up)** 또는 **Context**.
  - 특정 모달/입력 폼에만 닫힌 상태 ➔ **지역 `state`**.
  - 브라우저 새로고침 이후에도 유지할 상태 ➔ **외부 저장소(`localStorage`/IndexedDB)**와 동기화.

#### MoaBogo 저장소 연결 예시
1. **앱 전역 오케스트레이션 상태 (`src/App.tsx:62-155`)**:
   - `currentScreen`, `isLoggedIn`, `isOffline`, `deviceView`, `activeLedger`, `pendingQueueCount`는 헤더·드로어·커맨드 팔레트·하단 내비게이션·활성 화면이 동시에 읽고 바꿔야 하므로 최상위 `App`이 소유하고 각 화면에는 필요한 `props`와 콜백(`onBack`, `onToggleOffline`, `onSuccessLogin`)만 전달한다.
2. **전역 테마 Context (`src/context/ThemeContext.tsx:21-91`)**:
   - `theme`('light' | 'dark' | 'dawn' | 'system')과 OS 미디어 쿼리 결과 `systemIsDark`는 `state`로 소유하고, `resolvedTheme`과 `isDark`는 별도 `state`로 중복 저장하지 않고 렌더 중 **파생 계산(`L49-53`)**해 불일치를 원천 차단한다.
3. **제어(Controlled) vs 비제어(Uncontrolled) 하이브리드 (`src/sample/screen/SCR_OFF_01_오프라인동기화.tsx:34-41`)**:
   - `SCR_OFF_01`은 `externalIsOffline !== undefined ? externalIsOffline : internalOffline` 패턴으로 `App.tsx`에서 `isOffline`을 주입받으면 제어 컴포넌트로, 단독 렌더링 시에는 자체 `internalOffline` 상태로 동작한다.
4. **지역 폼 상태 (`src/components/TransactionModal.tsx:15-31`)**:
   - `txType`, `amount`, `merchantName`, `duplicateWarning`, `formError`는 모달 내부에 지역 `state`로 캡슐화하고, 소속 가계부 식별자(`activeLedger`)와 완료 알림(`onSuccess`, `onClose`)만 `props` 경계로 주고받는다.

#### 설계상 의미
- 상태 소유권이 분명할수록 백엔드 연결 시 교체가 쉬워진다. 예컨대 `TransactionModal`은 `activeLedger`를 `props`로 받고 저장은 `ledgerRepository.createTransaction`에 위임하므로 UI 상태와 데이터 영속 계층이 분리되어 있다. 반면 화면 컴포넌트가 `sample/data/*`를 직접 `import`해 초기 `useState`로 복사해 두면 외부 저장소와 컴포넌트 `state`의 진실 원천이 이원화된다.

### 3.3 렌더(Render)와 커밋(Commit) 단계

#### 핵심 원리
React 업데이트는 두 단계로 나뉜다.
1. **렌더(Render) 단계**: 컴포넌트 함수를 호출해 다음 UI 트리(React Element)를 계산하는 **순수 연산 단계**다. 이 단계에서는 DOM을 건드리거나 타이머/네트워크 부수효과를 일으키면 안 된다(`src/main.tsx:9`의 `<React.StrictMode>`가 개발 모드에서 렌더 함수를 두 번 호출해 순수성 위반을 조기에 드러낸다).
2. **커밋(Commit) 단계**: 계산된 차이를 실제 브라우저 DOM에 반영하고, `ref.current`를 연결한 뒤 `useEffect`를 실행하는 단계다.

#### MoaBogo 저장소 연결 예시
1. **렌더 단계의 순수 파생 계산 (`src/sample/screen/SCR_ROU_01_모아루틴.tsx:64-78`)**:
   - `enabledPlugins`와 `filterOptions`를 별도 `useEffect` + `setState`로 동기화하지 않고, 렌더 중 `useMemo`로 `pluginSettings`로부터 순수하게 파생한다. 불필요한 2차 재렌더(Cascading Render)를 피하는 정석 패턴이다.
2. **`key`와 커밋 인스턴스 교체 (`src/App.tsx:765-772`)**:
   - `<AppErrorBoundary key={currentScreen} ...>`에 `key={currentScreen}`을 부여해, 이전 화면에서 오류가 발생해 `hasError: true`가 되었더라도 사용자가 다른 화면으로 전환하면 React가 커밋 단계에서 기존 ErrorBoundary 인스턴스를 언마운트하고 새 인스턴스를 마운트해 오류 상태를 자동 초기화한다.
3. **커밋 이후 DOM/외부 속성 동기화 (`src/context/ThemeContext.tsx:76-82`, `src/App.tsx:128-133, 188-209`)**:
   - `ThemeProvider`는 `document.documentElement`의 `classList`와 `data-theme` 속성 변경을 렌더 본문이 아니라 `useEffect` 내부(커밋 이후)에서 수행한다.
   - `App.tsx`의 `mainRef`와 `deviceMenuRef` 역시 커밋된 실제 `<main>`, `<div>` DOM 노드를 가리키며, `scrollTo`·`contains` 같은 명령형 DOM 연산을 이벤트 핸들러 및 `useEffect` 안에서만 사용한다.

#### 설계상 의미
- 렌더 단계(순수 UI/파생 값 계산)와 커밋 이후 부수효과(DOM 제어, 네트워크, 로컬 스토리지)의 경계가 분명할수록 컴포넌트를 SSR/테스트/지연 로딩으로 옮기기 쉬워진다.

### 3.4 Hooks · `useEffect` · 정리(Cleanup) 동작

#### 핵심 원리
- `useEffect`는 **"화면을 외부 시스템(브라우저 이벤트, 타이머, 네트워크, IndexedDB, SSE)과 동기화"**하기 위한 탈출구다.
- 컴포넌트가 언마운트되거나 의존성 배열(`deps`) 값이 바뀌어 다음 effect가 실행되기 직전, React는 이전 effect가 반환한 **정리(cleanup) 함수**를 먼저 실행한다. 정리가 빠지면 메모리 누수, 중복 리스너, 늦게 도착한 이전 응답이 최신 상태를 덮어쓰는 **비동기 경합(Race Condition)**이 발생한다.

#### MoaBogo 저장소 연결 예시
1. **`AbortController` + 최신 `ref` 패턴 (`src/hooks/useApi.ts:22-130`)**:
   - `useApiQuery`는 `useEffect`마다 새 `AbortController`를 생성해 `fetcher(controller.signal)`에 전달하고, cleanup(`L64-66`)에서 `controller.abort()`를 호출한다. 또한 `if (!activeSignal.aborted)` 가드(`L41, 46, 51`)로 이미 취소·언마운트된 요청이 `setData`/`setError`를 호출하지 못하게 막는다.
   - `fetcherRef.current = fetcher`(`L31-32`) 패턴은 호출자가 인라인 화살표 함수를 넘겨도 `useEffect`가 매 렌더마다 재실행되는 무한 루프를 방지한다.
   - `useApiMutation`은 `activeControllerRef.current?.abort()`(`L105`)로 연속 호출 시 이전 요청을 취소하고, 언마운트 cleanup(`L93-97`)에서도 진행 중인 요청을 중단한다.
2. **전역 엔진 초기화와 대칭적 Teardown (`src/services/syncEngine.ts:222-294`, `src/App.tsx:117-125`)**:
   - `initSyncEngine()`은 ① `apiClient` 오프라인 Mutation 훅 등록, ② `setInterval` 주기 스케줄러, ③ `window` `online`·`OFFLINE_PREFS_UPDATED_EVENT` 리스너를 한 번에 설정하고, **정확히 대칭되는 해제 함수**(`registerOfflineMutationHook(null)`, `clearInterval`, `removeEventListener`)를 반환한다. `App.tsx:118-124`의 `useEffect`가 이를 반환값으로 연결해 `<React.StrictMode>`의 이중 마운트-언마운트-재마운트 검증에서도 리스너가 중복 누적되지 않는다.
3. **조건부 구독과 정리 (`src/App.tsx:136-146`, `src/components/CommandPalette.tsx:64-76`)**:
   - `App.tsx`의 `isDeviceMenuOpen` effect는 메뉴가 열렸을 때만 `mousedown` 리스너를 붙이고 닫히거나 언마운트될 때 해제한다. `CommandPalette.tsx`는 `keydown` 리스너를 `[isOpen, onClose]` 의존성에 맞춰 등록·정리한다.
4. **대조 사례 — 비동기 타이머 cleanup 주의 지점 (`src/sample/screen/SCR_OFF_01_오프라인동기화.tsx:56-81`)**:
   - `useEffect`(`L65-81`)의 `window` 이벤트 리스너는 반환 함수에서 정상 해제되지만, `showToast`(`L56-59`)의 `setTimeout(() => setFeedbackNotice(null), 3500)`는 별도 ref/cleanup 없이 호출되므로 연속 호출 시 이전 타이머가 새 토스트를 조기 종료할 수 있는 전형적인 타이머 관리 학습 사례다.

#### 설계상 의미
- `StrictMode` 환경에서도 훅이 안전하려면 **"등록한 모든 외부 구독·타이머·요청은 반드시 반환 cleanup에서 취소한다"**는 대칭성이 필수이며, 이를 `useApi`처럼 커스텀 훅으로 캡슐화할수록 개별 화면에서 실수할 여지가 줄어든다.

### 3.5 데이터 흐름과 FSD 모듈 경계의 설계상 의미

#### 핵심 원리
React의 **단방향 데이터 흐름(Unidirectional Data Flow)**은 위에서 아래로 `props`가 흐르고, 아래에서 위로 이벤트/콜백이 올라가는 구조다. FSD(Feature-Sliced Design)의 **단방향 레이어 의존성(`app ➔ pages ➔ widgets ➔ features ➔ entities ➔ shared`)**은 이 React 데이터 흐름을 파일·폴더 경계로 확장한 것이다.

#### MoaBogo 저장소 연결 예시
1. **단방향 포트(Port & Event Bridge) 패턴 (`src/sample/shared/ledgerTransferBridge.ts:69-120`, `src/sample/shared/securityGuards.ts:134-186`)**:
   - 모아루틴(`useMoaRoutine.ts:27`)이나 모아당번이 가계부에 자산이동(`TRANSFER`)을 기장할 때 가계부 화면(`SCR_LED_01`)을 직접 `import`하지 않고, 하위 공유 코어 `ledgerTransferBridge.ts`의 `publishLedgerTransfer()`를 호출한다.
   - 브릿지는 `securityGuards.ts`의 `maskAccountNumber`·`buildIdempotencyKey`·`sanitizeForLocalStorage`로 PII 마스킹과 중복 차단(멱등성)을 강제한 뒤 `CustomEvent`를 발행한다. 즉, 도메인 간 수평 결합 없이 하위 코어 포트를 경유해 이벤트를 전달하는 FSD 지향 설계다.
2. **HTTP 직렬화 파이프라인 (`src/services/apiClient.ts:83-267`, `src/services/caseTransform.ts`)**:
   - 프론트엔드(`camelCase`) ➔ `toSnakeCase` 직렬화 ➔ Express(`snake_case`) ➔ `toCamelCase` 역직렬화 흐름이 `apiClient` 단일 경계에 모여 있어, 각 화면·모달이 백엔드 네이밍 컨벤션에 오염되지 않고 React 친화적인 `camelCase` DTO를 유지할 수 있다.
3. **경계가 깨질 때 나타나는 현상 (설계 교훈)**:
   - 반대로 `src/services/`가 `src/sample/data/`와 `src/sample/screen/`을 직접 참조하거나, 화면 9종이 `sample/data`를 직접 `import`하면 **"화면(View) ➔ 훅/포트 ➔ 어댑터(Mock vs API)"** 경계가 무너져 백엔드 교체나 운영 번들 격리 시 화면 전체를 손봐야 하게 된다. 이 경계의 진단과 개선 계획은 [0055-01](./0055-01_코드리뷰-React_FSD_기반구조.md) 및 [0055-03](./0055-03_작업계획-FSD기반구조_계약단일화_및_DI격리.md)에 연결되어 있다.
