# 리뷰 운영 하네스

## 1. 목적과 작업 경계

모아보고의 기본 개발 흐름은 **세션작업**이다. 세션작업 안에서도 해당 작업에 필요한 리뷰를 수행할 수 있으며, **리뷰작업**은 여러 영역을 단계적으로 살피고 결과를 축적하는 집중 리뷰 흐름이다.

- **세션작업**: 승인된 작업계획에 따라 코드·설계·문서를 구현한다. 각 태스크의 `#태스크처리` 안에서 구현 결과를 리뷰하고, 현재 태스크 범위의 수정·리팩토링과 검증까지 마친 뒤 종료 시 작업리뷰로 기록한다.
- **리뷰작업**: 아키텍처·폴더구조·공통 정책·복수 화면/서비스 등 넓은 범위를 여러 단계에 걸쳐 탐색하고 근거를 기록한다. 리뷰 세션에서는 소스코드를 수정하지 않는다. 리뷰 결과, 이번 리뷰 세션에서 새로 만든 작업계획 및 로드맵에서 승인한 신규 참고자료만 작성·보완한다. 리뷰 보고서에는 해당 리뷰 세션의 결과와 회고도 기록한다.
- 세션작업 중 발견한 문제는 현재 승인된 태스크 범위 안에서 바로 수정·리팩토링하고 검증한다. 범위 밖의 발견만 백로그나 후속 계획으로 분리한다. 집중 리뷰에서 도출한 구현은 별도의 세션작업에서 수행하며, 집중 리뷰 세션 안에서는 리팩토링이나 버그 수정을 시작하지 않는다.
- 기존 리뷰 기록은 이력으로 보존한다. 현 리뷰 세션에서 작성한 리뷰 문서·작업계획·승인된 참고자료만 보완할 수 있다.

## 2. 리뷰 목적과 작업 흐름 선택

리뷰 진행 장소는 파일 수나 변경 줄 수로 자동 분기하지 않는다. **현재 세션의 목표와 리뷰의 호흡**을 기준으로 선택한다.

| 구분 | 판별 기준 | 진행 방식 |
|---|---|---|
| **태스크 처리 중 리뷰** | 현재 태스크의 구현 결과를 검토하는 상시 마무리 단계 | `#태스크처리`에서 구현 후 즉시 결과를 리뷰하고, 태스크 범위 내 수정·리팩토링과 테스트까지 진행한다. 결과는 `#태스크정리`에서 작업리뷰에 기록한다. |
| **집중 리뷰작업** | 전체 구조 감사, 여러 화면·서비스·계층을 가로지르는 분석, 공통 기준 수립, 여러 차례에 걸쳐 결과와 작업계획을 축적하는 리뷰 | 독립된 리뷰 모드로 진행한다. 리뷰 로드맵과 범위별 종료 조건을 두고, 필요하면 영역별 리뷰 세션으로 나눈다. |

위험도는 리뷰의 깊이·우선순위·필요한 전문성에 반영하며, 그것만으로 태스크 리뷰를 세션프롬프트 이후로 미루지 않는다. 사용자가 `#리뷰시작`을 요청하거나 태스크 범위를 넘어 여러 영역을 단계적으로 살피는 리뷰를 원하면 집중 리뷰 모드를 선택한다. 범위가 불명확하면 전체 감사를 임의로 시작하지 말고 대상과 제외 범위를 확인한다.

### 2.1 시점별 판단

1. **`#태스크처리`**에서 현재 태스크의 변경 결과를 리뷰하고, 범위 안의 수정·리팩토링·검증을 끝낸다. 이 작은/직접 연결된 리뷰를 `#세션프롬프트`까지 미루지 않는다.
2. **`#세션정리`**에서는 태스크별 리뷰·검증이 반영된 구현 결과를 기록하고 다음 세션작업의 시작 프롬프트를 제공한다. 필요하다면 별도의 집중 리뷰 후보와 시작 프롬프트를 구분해 함께 제공한다.
3. **`#세션프롬프트`**는 선택 단계다. `#세션정리`에서 제공한 다음 세션작업·집중 리뷰 후보를 재확인하거나, 중간에 나온 다음 작업 의견을 반영해 프롬프트를 보완·재작성한다. 이를 필수 게이트로 두지 않는다.
4. 집중 리뷰 후보를 제안하거나 시작 프롬프트를 작성할 때는 이 하네스를 참조해 목적과 대략적인 범위를 판단한다. 실제 범위와 단계는 새 리뷰 세션의 `#리뷰시작`에서 대상 코드를 확인한 뒤 확정한다.
5. 선택된 집중 리뷰는 `#세션시작`에서 리뷰 모드로 세션을 초기화한 다음 `#리뷰시작`으로 진입한다. 일반 작업 모드의 `#태스크시작`은 실행하지 않는다.

전체 구조 감사의 기본 기준은 첫 리뷰 시작 시점의 원격 `dev` HEAD SHA다. 최초 로드맵과 후속 영역 리뷰는 별도 합의가 없는 한 같은 SHA를 사용한다. 특정 PR이나 다른 기준이 목적에 더 맞으면 사용자가 지정한 기준을 기록한다. 움직이는 브랜치를 검토할 때는 시작 시점의 대상 SHA와 비교 기준을 기록한다. 리뷰 대상 코드를 체크아웃하거나 브랜치를 바꿔야 한다면 기존 작업 트리의 변경을 먼저 보호하고, 사용자 변경을 덮어쓰지 않는 격리 방법을 사용한다.

## 3. 리뷰 산출물과 번호

모든 정식 리뷰는 세션작업과 동일한 **전역 세션 번호 체계**를 사용한다. 리뷰 전용 번호를 별도로 발급하지 않는다. 파일명은 다음 형식을 따른다.

```text
{세션번호}-{문서순번}_작업리뷰-{주제}.md
{세션번호}-{문서순번}_코드리뷰-{주제}.md
{세션번호}-{문서순번}_작업계획-{주제}.md
{세션번호}-{문서순번}_참고자료-{주제}.md
```

예시:

```text
0099-01_코드리뷰-서비스별공유메타정보.md
0099-02_작업계획-공유URL메타정보분리.md
0099-03_참고자료-React핵심개념과프로젝트적용.md
0100-01_작업리뷰-공유기능개선.md
```

- **작업리뷰**: 세션작업의 요구사항, 태스크 처리 중 수행한 결과 리뷰·범위 내 리팩토링, 실제 변경 내용, 검증 결과, 남은 과제를 기록한다.
- **코드리뷰**: 구현을 수행하지 않고 고정된 코드 기준선 또는 변경분을 검토한 발견사항, 영향도, 우선순위, 근거, 권고안과 검증 기준을 기록한다. 발견사항이 없더라도 범위와 미검증 영역을 남긴다.
- **작업계획**: 코드리뷰 결과로 구현이 필요할 때 작성한다. 목표·범위·영향 파일·순서·검증 기준·완료 조건을 담고, 연관 코드리뷰 문서를 서로 링크한다. 관련 발견사항은 화면·공통영역·우선순위·의존성에 따라 실행 가능한 단위로 묶는다.
- **참고자료**: 리뷰 이해에 필요한 별도 학습·배경 자료가 로드맵에서 승인된 경우에만 새로 작성한다. 코드리뷰와 구분해 개념 설명, 저장소 내 예시, 설계상 의미를 담고 연관 리뷰 문서에서 링크한다.
- 문서순번은 세션 내 모든 작업리뷰·코드리뷰·작업계획·참고자료 산출물에 걸쳐 중복되지 않게 증가시킨다. 구현은 새 세션 번호를 받아 작업계획과 연결한다.
- 기존 문서는 이력과 링크 안정성을 위해 파일명을 유지한다. 새 문서부터 위 유형명을 파일명에 사용한다.

## 4. 집중 리뷰 로드맵과 검토 기준

전체 구조를 살피는 리뷰는 첫 리뷰 세션의 코드리뷰 문서에 목적, 시스템 기준선, 제외 범위, 단계 순서, 완료 조건을 담은 로드맵을 둔다. 로드맵과 완료된 리뷰 문서는 이력으로 보존하며 후속 세션에서 수정하지 않는다. 각 후속 리뷰 문서에 부모 로드맵 링크, 기준 SHA, 영역별 최신 상태 스냅샷(`미검토 / 검토완료 / 제외(근거)`), 이번 세션 범위를 기록해 진행을 이어간다. 기준이 달라지는 것을 막기 위해 첫 영역에서 공통 판단 기준을 정하고 이후 영역에서도 재사용한다.

MoaBogo의 전체 프론트엔드 구조 리뷰는 다음 순서를 기본안으로 삼되, 발견에 따라 조정한다.

1. **기반 구조**: 저장소·폴더·모듈 경계와 의존성 방향·순환참조를 점검한다. React의 컴포넌트 조합, props/state, 렌더·커밋, hooks/effect·정리 동작 및 데이터 흐름을 학습하고 현재 코드에 연결한다. 이번 구조 리뷰에서는 React 핵심 개념·저장소 예시·설계상 의미를 별도 참고자료로 작성하고, 코드 진단 결과는 코드리뷰 문서에 따로 기록한다.
2. **공통 기반**: 공통 컴포넌트, 디자인 정책과 토큰의 정의·사용·누락·중복, 접근성 및 반응형 적용을 살핀다.
3. **도메인·서비스**: 도메인 모델, 서비스 경계, 객체지향 설계와 서비스별 디자인 패턴의 적합성을 검토한다.
4. **화면별 구조**: 화면·컴포넌트 책임, 파일 분리와 크기, 중복 및 화면별 실행 가능한 개선계획을 검토한다.
5. **운영·품질 횡단 검토**: 비동기 이벤트와 경합, 오류·로딩·복구, 캐시, 동기화·원자성, 테스트 전략·커버리지·테스트 용이성, 성능과 관측 가능성을 살핀다. 보안·개인정보 경계도 해당 데이터 흐름에서 확인한다.

이 순서는 조사 가이드이지 특정 패턴이나 기술 도입을 미리 정하는 기준이 아니다. 이벤트·캐시·원자성 등은 일관성, 성능, 장애 복구 요구와 근거가 확인될 때만 개선안으로 제시한다.

### 발견사항과 완료 기준

각 발견사항은 다음 정보를 갖춘다.

- 근거(파일·라인 또는 재현 가능한 흐름), 현재 동작, 영향 범위
- 우선순위/심각도와 판단 확신도, 관련 의존성·미검증 영역
- 개선 권고와 측정 또는 재현 가능한 완료·검증 조건

우선순위는 `P0(즉시 대응: 데이터 손실·보안 침해·핵심 흐름 중단)`, `P1(높음: 주요 기능 또는 유지보수에 큰 영향)`, `P2(보통: 제한된 영향이나 반복되는 구조적 비용)`, `P3(낮음: 개선 기회)`로 일관되게 사용한다. 확신도는 `높음/보통/낮음`으로 표시하며, 낮은 확신의 가설은 확인된 결함과 구분해 검증 과제로 남긴다.

각 리뷰 단계는 지정 범위의 검토 상태와 미검증 항목을 명시하고, 발견사항을 우선순위·의존성에 따라 작업계획으로 묶었을 때 완료로 본다. 개선안은 현재 구조와 목표 구조의 차이 및 단계적 전환 경로를 설명하며, 전면 재작성은 근거가 있는 경우에만 제안한다.

## 5. 폴더와 기록량 관리

```text
docs/08.리뷰/
├── README.md
├── 01.작업리뷰/
│   ├── 세션0001-0025/
│   ├── 세션0026-0050/
│   └── 세션0051-0075/
└── 02.코드리뷰/
    └── 세션0001-0025/
```

- 완료한 세션의 구현 결과 문서는 `01.작업리뷰`에 둔다.
- 독립 코드리뷰와 그 리뷰에서 파생된 작업계획·참고자료는 `02.코드리뷰`의 동일한 세션 범위 폴더에 둔다. 파일명으로 `코드리뷰`, `작업계획`, `참고자료` 유형을 구분한다.
- 폴더는 25개 세션 번호 단위로 나눈다. 한 범위 폴더가 문서 50개를 넘으면 해당 범위를 10개 세션 단위의 하위 폴더로 세분화한다.
- 이미지 등 리뷰 보조자료는 해당 작업리뷰 세션 범위 아래에 둔다. 문서에서 상대경로로 연결하고, 파일명은 관련 세션/문서를 식별할 수 있게 한다.
- 과거 문서는 내용의 목적을 기준으로 재분류하되, 원문과 파일명은 유지하고 이동에 따른 내부·외부 문서 링크만 갱신한다. 구현 완료 기록은 제목에 “코드리뷰”가 있더라도 작업리뷰에 둔다. 구현 없이 코드 구조·위험·결함을 분석한 자료는 코드리뷰에 둔다.

## 6. 리뷰 단계

### `#리뷰시작` (집중 리뷰 모드)

1. 집중 리뷰 모드와 해당 세션의 목적을 확인한다. 세션작업 안의 리뷰는 현재 작업 흐름에서 다루며, 별도 `#리뷰시작` 절차로 전환하지 않는다.
2. 목적, 포함·제외 범위, 기준일을 확정한다. 전체 구조 감사는 최초 원격 `dev` HEAD SHA를 기록하고 후속 세션도 같은 기준을 사용한다. 특정 PR 등 다른 기준을 요청받으면 그 기준을 기록한다. 넓은 감사는 단계별 범위와 완료 조건도 정한다.
3. 정식 리뷰는 세션작업과 같은 전역 번호를 사용한다. `#세션시작`의 공통 초기화 후 `#리뷰시작`을 진행하며, 태스크 구현 계획 단계로 보내지 않는다.
4. `git status`로 기존 미커밋 변경을 확인하고 요청된 대상만 검토한다. 대상 코드는 고정된 diff/SHA를 근거로 읽고, 기존 변경을 임의로 리뷰에 포함하거나 스테이징·초기화·덮어쓰지 않는다. 충돌 우려가 있으면 먼저 사용자에게 확인한다.
5. 코드·기존 기록은 읽기 전용으로 다룬다. 소스 수정이나 기존 기록 덮어쓰기는 금지한다.
6. 새 코드리뷰 문서를 만들고, 목적·대상 SHA·범위·제외 항목·단계·미검증 영역을 기록한다. 별도 참고자료가 로드맵에서 승인되었다면 새 파일로 작성해 코드리뷰 문서와 연결한다.

### `#리뷰처리`

1. 지정된 단계와 범위만 검토하고, 발견사항마다 우선순위/심각도, 근거(파일·라인 또는 변경 내용), 영향, 확신도, 의존성, 권고안, 검증 가능한 완료 조건을 기록한다.
2. 발견사항이 없으면 검토한 범위, 확인한 기준, 미검증 영역을 기록한다.
3. 구현이 필요하면 관련 발견사항을 화면·공통영역·우선순위·의존성에 따라 묶어 새 작업계획을 만들거나 이번 리뷰 세션에서 만든 계획을 보완한다. 계획의 승인과 구현 착수는 별개다.
4. 코드나 다른 기존 문서는 수정하지 않는다. 구현은 `#세션시작`과 `#태스크처리`를 거치는 별도 세션작업에서 한다.

### `#리뷰정리`

1. 코드리뷰 발견사항과 근거·우선순위·확신도·미검증 영역, 단계 상태, 작업계획 링크 및 상태를 최종 점검한다.
2. 리뷰 결과와 세션 회고를 리뷰 문서에 반영한 뒤, 리뷰 산출물만 포함한 문서 PR을 `dev`에 병합한다. 구현 코드 변경이나 구현 PR을 리뷰 PR에 섞지 않는다.
3. 문서 링크, 부모 로드맵의 상태 스냅샷, 부모 문서 인덱스와 다음 행동을 확인한다. 완료된 과거 리뷰 문서는 수정하지 않는다. 넓은 감사는 후속 리뷰 단계가 남았는지 명시한다.

### `#리뷰승급`

`#리뷰정리`에서 리뷰 PR이 `dev`에 병합된 뒤 `node agentwork/gh-cli.cjs sync-branches`와 `node agentwork/gh-cli.cjs status`로 최종 `dev` → `stg`/`main` 동기화와 SHA 일치를 확인한다. 오픈 PR이 없는지 확인하고 `node agentwork/gh-cli.cjs close-issue --issue <리뷰세션이슈번호>`로 이슈를 닫은 뒤 세션 상태를 완료 처리한다. 집중 리뷰 세션은 이 절차가 세션 마감까지 담당하므로 별도의 `#세션정리`를 호출하지 않는다. 이 단계는 리뷰 문서만 승급하며 제품 코드를 배포하지 않는다. 계획 구현은 새 세션작업으로 시작한다.

### `#세션프롬프트`

`#세션프롬프트`는 선택적으로 사용한다. `#세션정리`에서 이미 제공한 다음 세션작업과 별도 집중 리뷰 후보를 재확인하거나, 진행 중에 나온 다음 작업 의견을 반영해 시작 프롬프트를 보완·재작성한다. 두 흐름이 모두 유효하면 각각 구분해 제시하고, 한 흐름만 유효하면 그 흐름만 제시한다. 리뷰 시작 프롬프트를 새로 만들거나 보완할 때는 이 하네스를 다시 확인한다. 집중 리뷰 세션의 다음 단계는 `#리뷰승급` 결과와 로드맵을 바탕으로 제안한다.
